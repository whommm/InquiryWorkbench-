# SmartProcure 系统优化设计文档

- 文档版本: `v1.0`
- 编写日期: `2026-02-16`
- 适用范围: `smart-procure`（后端、前端、部署链路）

## 1. 背景与目标

### 1.1 背景

当前系统已具备完整业务闭环（询报价表格、AI 助手、供应商管理与推荐、部署脚本），但存在典型的“功能可用、工程化待增强”问题：

- 关键路由文件体量过大，维护与回归成本高。
- 管理接口权限边界偏弱，安全风险高于业务容忍范围。
- 部分状态依赖内存，重启和多实例场景下存在数据丢失。
- AI 调用与结构化输出的异常兜底不够系统化。
- 前端大表格编辑链路在规模增大时有性能退化风险。
- 编码与文案存在乱码问题，影响用户体验和 Prompt 稳定性。

### 1.2 优化目标

本轮优化聚焦“稳定性、安全性、可维护性、可观测性”，不改动核心产品交互范式。

目标指标：

- `P0` 接口（登录、聊天、保存）可用性达到 `99.9%`。
- 管理类接口具备完整 RBAC 保护，普通用户无越权入口。
- 异步任务与通知链路不依赖进程内存，支持多实例部署。
- `routes.py` 完成模块拆分，后端结构清晰可测试。
- 增加关键链路自动化测试，覆盖登录、聊天写入、供应商推荐。
- 清理编码问题并统一 UTF-8，消除页面与日志乱码。

### 1.3 非目标

- 不在本轮重做业务流程和页面信息架构。
- 不更换核心技术栈（FastAPI/React/Univer/Qdrant）。
- 不引入复杂微服务拆分，保持单体应用演进。

## 2. 现状评估

### 2.1 架构现状

- 后端: `FastAPI + SQLAlchemy + JWT + Qdrant + Playwright`
- 前端: `React + TypeScript + Zustand + Univer`
- 部署: `Docker Compose`（dev/prod）+ `Nginx`

### 2.2 主要问题分级

`P0`（必须先处理）：

- 路由聚合过重：`smart-procure/backend/app/api/routes.py`
- 管理接口缺少管理员权限隔离：`/api/admin/embeddings/*`
- 通知与任务结果使用进程内存 `_user_notifications`

`P1`（建议本轮处理）：

- LLM 调用统一超时/重试/熔断策略缺失：`app/core/llm.py`
- 文件编码和中文文案乱码影响体验与规则匹配
- 前端大数据量编辑时全量更新链路开销偏大

`P2`（下一轮持续优化）：

- 更细粒度的可观测性（Tracing、Prometheus 指标）
- 更完善的前端 E2E 覆盖和性能基准体系

## 3. 设计原则

- 渐进式重构：每个阶段可独立发布、可回滚。
- 业务无中断：优先“兼容扩展”，避免一次性大改。
- 安全默认开启：鉴权、限流、审计作为默认能力。
- 可观测先行：优化必须带监控和日志证据。
- 以测试保变更：核心流程先补测试再重构。

## 4. 优化方案设计

### 4.1 后端模块拆分与分层治理

#### 4.1.1 目标

将超大路由按业务域拆分，降低认知复杂度和回归风险。

#### 4.1.2 方案

建议目录重构（示意）：

```text
backend/app/api/
  __init__.py
  deps.py
  routers/
    auth.py
    chat.py
    sheets.py
    suppliers.py
    admin.py
    notifications.py
```

落地策略：

- 保持现有 URL 不变，仅迁移实现位置。
- 公共依赖注入（`get_current_user`、DB session）统一到 `deps.py`。
- 统一错误响应结构（错误码、错误消息、trace_id）。

### 4.2 权限与安全治理（RBAC）

#### 4.2.1 目标

管理接口仅允许管理员调用，并提供可审计操作记录。

#### 4.2.2 方案

- 在 `users` 表增加字段 `role`（`user/admin`）。
- 新增依赖 `require_admin`，用于 `/api/admin/*`。
- 对高风险操作增加审计日志（调用人、时间、参数摘要、结果）。
- 为登录与关键写接口增加限流（Nginx 或应用层）。

### 4.3 异步任务与通知持久化

#### 4.3.1 目标

去除进程内存状态依赖，支持多实例/重启场景的数据一致性。

#### 4.3.2 方案

- 用消息队列替换 `BackgroundTasks` 的关键任务链路（建议 Redis + RQ/Celery）。
- 通知改为持久化存储（表 `notifications`），前端按用户拉取未读通知。
- 任务执行增加幂等键，避免重复写入供应商或重复索引。

### 4.4 AI 网关稳定性增强

#### 4.4.1 目标

保证 LLM 异常时系统可降级，不阻断核心业务。

#### 4.4.2 方案

- 封装统一 LLM Gateway：
  - 超时控制（建议 `15-20s`）
  - 指数退避重试（建议 `2` 次）
  - 熔断与短路降级（返回结构化 ASK）
- 对 Planner/Writer 输出执行 JSON Schema 校验。
- 增加 Prompt 版本号，便于灰度和回滚。
- 记录关键指标：耗时、重试次数、解析失败率、工具调用成功率。

### 4.5 前端性能与状态流优化

#### 4.5.1 目标

降低大表格编辑时卡顿和无效重渲染，保证交互流畅性。

#### 4.5.2 方案

- `UniverSheet` 变更上报由“高频全量”改为“节流+批量”。
- `TabsStore` 更新改为分块持久化（必要时引入 patch 模型）。
- 聊天消息与表格更新分离状态，减少互相触发重渲染。
- 明确“脏数据”策略：本地脏标记、手动保存、失败重试提示。

### 4.6 编码与文案治理

#### 4.6.1 目标

统一编码与文本资产，消除乱码和语义偏差。

#### 4.6.2 方案

- 全仓统一 UTF-8（无 BOM），新增 `.editorconfig` 和 pre-commit 校验。
- 扫描并修复后端提示词、前端 UI 文案、README 文档乱码。
- 将高频中文常量统一沉淀（后端常量模块 / 前端 i18n 预留）。

### 4.7 部署与工程链路优化

#### 4.7.1 目标

降低部署不确定性，保证开发/生产行为一致。

#### 4.7.2 方案

- 清理 `deploy/Dockerfile.frontend` 中与 dev/prod 混杂的冗余指令。
- 增强启动自检：环境变量完整性、外部服务连接性（DB/Qdrant）。
- 增加 CI 流程：`lint + unit test + build + smoke test`。

## 5. 数据库与接口变更设计

### 5.1 数据库变更（建议）

1. `users.role`（默认 `user`）
2. `notifications`（用户通知）
3. `task_runs`（任务追踪，可选）
4. `supplier_products` 索引优化（`brand/product_model/supplier_id`）

### 5.2 接口兼容策略

- 维持现有 API 路径不变，避免前端联调成本。
- 新增字段采取“向后兼容”返回，不删除旧字段。
- 管理接口新增 `403` 场景，前端提示“权限不足”。

## 6. 实施计划（分阶段）

### Phase 0: 基线与保护（1 周）

- 补齐关键链路测试（登录、聊天、保存、推荐）
- 记录当前性能与错误率基线

### Phase 1: 安全与结构（1-2 周）

- 路由拆分
- RBAC 落地
- admin 接口权限收口

### Phase 2: 异步与 AI 稳定性（2 周）

- 通知持久化
- 异步任务队列化
- LLM Gateway 与 JSON 校验

### Phase 3: 前端性能与编码治理（1-2 周）

- 表格状态更新优化
- UTF-8 全仓修复与文案清理
- 体验回归测试

### Phase 4: 灰度与收尾（1 周）

- 预发灰度
- 指标验收
- 回滚演练与文档归档

## 7. 验收标准

功能验收：

- 所有原有业务流程可用且回归通过。
- 管理接口非管理员访问返回 `403`。
- 通知在服务重启后可继续读取。

质量验收：

- `P0` 链路自动化测试通过率 `100%`。
- 线上关键接口 5xx 下降到目标区间。
- AI 输出结构化解析失败率显著下降。

体验验收：

- 前端大表格编辑不卡顿（主观体验明显提升）。
- 页面与日志不再出现中文乱码。

## 8. 风险与回滚

主要风险：

- 路由拆分期间接口行为偏移
- 异步化改造导致任务时序问题
- 编码修复引入文本匹配副作用

回滚策略：

- 每阶段独立发布，保留旧实现开关（feature flag）
- 数据库迁移提供 down 脚本
- 关键改造前创建可恢复备份

## 9. 优先落地清单（建议先做）

1. `/api/admin/*` 加 RBAC
2. 拆分 `routes.py`（优先 `suppliers/sheets`）
3. 引入 LLM 超时+重试+结构化校验
4. 通知从内存改为持久化
5. 全仓 UTF-8 与乱码修复
